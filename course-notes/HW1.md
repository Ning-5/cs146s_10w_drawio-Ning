# HW1 实验报告：让本地小模型把流程描述变成可渲染规格



## 1. 实验概述与假设



本作业的目标是让本地模型（qwen3:4b-q4_K_M）把中文自然语言流程描述转换成机器可渲染的 JSON 规格（包含 `nodes` / `edges` / `questions` 三个字段），并通过 preview.py 渲染为 SVG 和 draw.io 格式。课程提供了三种提示策略：



- **brief**：只给最简任务描述，不给输出格式说明；

- **contract**：明确给出 JSON 字段结构、id 命名规则、"模糊处放入 questions"等约定；

- **schema**：在 contract 基础上以 JSON Schema 形式硬约束输出结构。



实验在 dev（D1–D4）和 eval（E1–E4）两个 split 上进行，每个案例 3 种模式 × 2 次重复，共 48 次调用。



**实验假设**：三种模式的可靠性差异主要来自输出约束的强度——brief 缺少结构约定，模型自由发挥导致输出无法解析；contract 给出约定但依赖模型自觉遵守；schema 用硬约束封死格式自由度，理论上应最稳定。 Eval split 的案例含有更复杂的语义陷阱（歧义、冲突、留白），预计会暴露各模式在"含义表达"层面的差异。



## 2. 检查定义



### 2.1 程序化格式检查（四关）



| 检查项 | 含义 |

|---|---|

| `json_parse` | 输出能被 `json.loads` 解析为合法 JSON |

| `edge_fields` | 每条边都包含 `source` / `target` 字段 |

| `edge_refs` | 每条边的 source / target 都能对应到 nodes 中已有的 id |

| `unique_ids` | 节点 id 无重复 |



### 2.2 人工含义判断（四问）



程序检查只覆盖格式层，"结构正确"不等于"需求表达正确"。对每个通过格式检查的输出，人工回答四个问题：



1. 原文中的步骤是否都被保留（无遗漏）？

2. 分支、回路、并行关系是否与原文一致？

3. 原文中模糊 / 冲突 / 留白的信息，是否用 `questions` 恰当表达（该问的有问，不该编的没编）？

4. 是否添加了输入中没有的内容（自行拍板、编造角色、擅自解决冲突）？



## 3. 主要发现



### 3.1 结果总表（四关全过计为通过）



| 模式 | dev (4 案例 × 2) | eval (4 案例 × 2) | 合计 |

|---|---|---|---|

| brief   | 0/8  | 0/8  | **0/16** |

| contract | 8/8  | 6/8  | **14/16** |

| schema  | 8/8  | 8/8  | **16/16** |



### 3.2 brief：全军覆没



brief 模式 16 次调用全部失败在 `json_parse` 上。原因高度一致：qwen3 是推理模型，会先输出 `<think>…</think>` 的思考文本再给答案，brief 模式下没有格式约定压制这种行为，首字符几乎从不是 `{`，解析必挂。这证明**提示中的格式约定不是可选项，而是解析前提**。



### 3.3 contract：dev 满分但 eval 暴露风险



contract 在 dev 上 8/8，在 eval 上 6/8，两次失败都发生在 E4（报销规则冲突案例），败因是 **ReadTimeout（约 300 秒上限）**而非格式错误——模型在无 schema 约束时输出过长、收敛慢。dev 的满分存在小样本运气成分，eval 暴露了它在复杂案例上的真实风险。



### 3.4 schema：满分且更快收敛



schema 模式 16/16 全过，且同样在 E4 上以 117–217 秒跑完（contract 同案例直接超时）。**硬约束不仅保证格式，还通过限制输出空间加速了收敛**——这与实验假设一致。



## 4. 实现与改进记录（改前 / 改后另列）



### 4.1 改前：首次运行中断



- Run ID：`20261115-170839`

- 现象：运行中途崩溃，Traceback 显示 `json.loads` 对空字符串 / None 抛异常，单个失败请求直接终止整个 run。

- 教训：网络层和解析层都必须有失败保护，"一条失败全盘崩"不可接受。



### 4.2 改后：完整跑通



- 改动：给请求调用加了 timeout 保护、给解析加了 try/except，失败请求的错误被记录到对应案例文件中，run 继续执行其他案例。

- 效果：dev run（`20261115-171410`）和 eval run（`20261115-174554`）各自完整跑完 24 条记录，brief 全灭时也全部留下失败原因，符合 HW1"失败请求保存错误、继续跑其他案例"的要求。



### 4.3 环境坑（与本作业无关但值得记录）



- **BOM 坑**：PowerShell 5.1 的 `Out-File -Encoding utf8` 写出的文件带 UTF-8 BOM，preview.py 用 `encoding="utf-8"` 读取时报 `Unexpected UTF-8 BOM (decode using utf-8-sig)`。解决：改用 .NET `[System.IO.File]::WriteAllText` + `UTF8Encoding($false)` 写无 BOM 文件。

- **GBK 显示坑**：`type` 命令按 GBK 解码 UTF-8 文件导致中文乱码，纯属控制台显示问题，文件本身是好的。改用 `Get-Content -Encoding UTF8` 解决。



## 5. 人工含义判断：格式正确 ≠ 需求正确



这一节回答完成标准中"至少举出一种格式正确但含义有问题的情形"。



### 5.1 三个模范输出



- **D3（contract，focus：保留已知信息并提出问题）**：原文明确说"无货怎么办还没有决定"，模型在图中画出问号节点"无货怎么办？"、在 `questions` 中提问"无货怎么办？"——该问的问了，没有自行编造解决方案。

- **D4（contract，focus：识别冲突，不自行决定）**：原文前后矛盾（审核前 / 审核后都要发同一确认）。模型把两个互相矛盾的版本都作为节点摆出，`edges` 留空，`questions` 直接点破："审核前和审核后是否需要发送同一确认？是否存在流程冲突？"——冲突被识别、被呈现、被提问，零自行拍板。

- **E3（schema，focus：歧义与待确认问题）**：原文"交给他批准"中的"他"未指明。模型把"交给他批准"原样保留为节点 label，没有把"他"具体化为某个角色，`questions` 追问"这里的『他』具体指代谁？"——没有编造输入中不存在的实体。



### 5.2 反例：E4（schema）格式满分但含义不合格



- **现象**：E4 的 schema 输出 `json_parse` / `edge_fields` / `edge_refs` / `unique_ids` 四关全过，图结构完整（六个节点、六条边，两条规则画成并行分支）。

- **问题**：原文给出两条互相冲突的报销规则（>1000 元需主管批准 vs >800 元直接支付），规则在 800–1000+ 元区间同时覆盖且结论矛盾。但输出中的 `questions` 放的是**两条陈述句**（"报销金额 > 1000 元：需要主管批准"、"报销金额 > 800 元：直接支付"），根本不是问题——规则之间的真正冲突没有被指出，模型只是把矛盾**并行排列**成了一套看似自洽的流程。

- **定性**：对照 focus"冲突关系与提问"——**格式满分、含义不合格**。这是"结构正确"与"需求表达正确"存在鸿沟的直接例证：程序检查无法判断 questions 里放的是真问题还是陈述句，更无法判断冲突是否被识别。



### 5.3 附赠发现：检查器的边界情况



D3 contract 输出中，节点 id 为 `What_to_do_if_out_of_stock`（大写 W），而边引用的是 `what_to_do_if_out_of_stock`（小写 w），大小写不一致，但 `edge_refs` 检查照样通过——说明引用比对存在宽容匹配。这提醒我们：**pass 不等于完全一致，格式检查有盲区**。



## 6. 选定的输出



选定 **D1（contract，r1）** 作为最终交付规格：



- dev run `20261115-171410`，D1-contract-r1.json，耗时 35.61 秒，四关全过；

- 渲染结果为三节点两边的退货流程图：接收退货 → 完成质检 → 登记入库；

- D1 原文是最干净的三步顺序流程，无歧义 / 冲突 / 留白，因此 `questions` 为空数组是**合理的**——没有该问的问题就不该硬凑问题，这本身也是"不添加输入中没有的内容"原则的体现。



交付文件（`.runtime/hw01/` 下）：



- `chosen-spec.json`（提取后的纯规格，无 BOM）

- `chosen.svg`（浏览器验收：中文 label 完全正常）

- `chosen.drawio`（draw.io 格式，HW2 手工编辑的起点）



## 7. 需用户确认的信息



综合人工分析，若此流程图要投入实际使用，以下信息需要向需求方确认：



1. **D3**：库存不足时的处理方式（原文明确留白）；

2. **D4**：确认到底应在审核前还是审核后发送（原文冲突）；

3. **E3**："交给他批准"中的"他"具体是哪个角色（原文歧义）；

4. **E4**：>1000 与 >800 两条规则冲突时以哪条为准（模型未指出，人工补充发现）。



## 8. 局限与下一步



- **单模型**：只测了 qwen3:4b-q4_K_M，结论不能外推到其他模型；

- **小样本**：8 案例 × 2 重复，contract 在 dev 与 eval 上的波动提示需要更多重复次数才能给出稳定通过率；

- **检查器盲区**：大小写宽容匹配这类边界情况说明格式检查本身也需要测试；

- **下一步**：HW2 将在 `chosen.drawio` 基础上手工编辑完善，并观察人工介入后规格的变化。
